1. GROUND CONTROL STATION — TELEMETRY RECEPTION AND DECODING
================================================================================

[A] Receive telemetry via IPC or sockets; decode within 3 ms
    Proof:
      - Transport: TCP length-delimited frames from satellite (see ground main:
        TcpListener on SIM_TCP_PORT, telemetry_rx uses FramedRead).
      - Decode budget: shared::config::TELEMETRY_DECODE_MS = 3 (milliseconds).
      - Log: ground.log lines tagged "telemetry_rx" include decode_us=… (µs).
      - Violation log: "DECODE DEADLINE MISSED (>3ms)" increments
        decode_deadline_misses in gcs_final_report.txt.

    Quick search:
      rg "telemetry_rx|DECODE DEADLINE" .\ground.log
      type .\gcs_final_report.txt | findstr decode

    Code: ground\src\telemetry_rx.rs (deserialize + decode duration check)
          shared\src\config.rs (TELEMETRY_DECODE_MS)

[B] Log packet reception latency and reception drift
    Proof:
      - Same "telemetry_rx" INFO lines: latency_us (GCS recv − packet timestamp),
        drift_us (actual inter-arrival − nominal period for that sensor).

    Quick search:
      rg "telemetry_rx sensor=" .\ground.log

[C] Trigger re-requests on missing/delayed packets
    Proof:
      - Sequence gap: "PACKET LOSS DETECTED — enqueuing RequestTelemetry" and
        uplink "RequestTelemetry" / telemetry_rx RequestTelemetry enqueue log.
      - Delayed (no frame but overdue vs 1.5× expected period):
        "DELAYED PACKET DETECTED — enqueuing RequestTelemetry".

    Quick search:
      rg "PACKET LOSS|DELAYED PACKET|RequestTelemetry" .\ground.log

    Rollup: gcs_final_report.txt → re_request_count, delayed_packet_events

[D] Simulate "loss of contact" if ≥3 packets fail in sequence
    Proof:
      - Gaps: "SATELLITE LOSS OF CONTACT: 3+ gaps detected" (sequence losses).
      - Delay streak: "SATELLITE LOSS OF CONTACT: 3+ delayed packets in sequence".
      - State moves to LossOfContact; contact_status becomes LOST in UI metrics.

    Quick search:
      rg "LOSS OF CONTACT" .\ground.log

2. GROUND CONTROL STATION — COMMAND UPLINK SCHEDULER
================================================================================

[A] Maintain a real-time command schedule
    Proof:
      - BinaryHeap priority queue (priority + timestamp) in ground main and
        uplink_tx; periodic 5 ms dispatcher loop.

    Code: ground\src\main.rs (cmd_queue), ground\src\uplink_tx.rs

[B] Enforce deadlines for urgent commands (≤2 ms dispatch)
    Proof:
      - uplink_tx: tokio::time::timeout with deadline_ms = 2 when
        cmd.packet.priority <= 2 (urgent / emergency), else CMD_DISPATCH_MS (also 2).
      - Success path logs dispatch_us; failure: "DISPATCH DEADLINE MISSED".

    Quick search:
      rg "DISPATCH DEADLINE|uplink_tx: sent" .\ground.log

    Rollup: gcs_final_report.txt → cmd_deadline_misses

[C] Validate commands against system state (safety interlocks)
    Proof:
      - While GcsSystemState is InterlockActive or LossOfContact, commands with
        priority > 1 are not sent; logged as COMMAND REJECTED with a reason string.

    Quick search:
      rg "COMMAND REJECTED" .\ground.log

    Rollup: cmd_rejected_count, cmd_rejection_last_reason

    Note: Heartbeats are priority 3 every 5 s; interlock clear is ~50 ms after a
    fault. That narrow window often yields zero COMMAND REJECTED lines in a clean
    run. To almost always capture rejections: leave GCS running but stop the
    satellite for ≥10 s (packet-loss timer + LossOfContact) while GCS keeps
    enqueueing heartbeats — then rg "COMMAND REJECTED|loss_of_contact" .\ground.log
    Rejection reasons are explicit in logs and in cmd_rejection_last_reason:
      - interlock_active_non_emergency_blocked
      - loss_of_contact_non_emergency_blocked

[D] Log command deadline adherence and rejection reasons
    Proof:
      - Adherence: each "uplink_tx: sent" includes dispatch_us; misses logged.
      - Rejections: "COMMAND REJECTED" with reason= field (tracing) and TUI/file
        log lines including the reason suffix in parentheses.

================================================================================
6. KNOWN LIMITATIONS / HOW TO READ THE FINAL REPORT
================================================================================

- Latency histogram percentiles (latency_p50_us, etc.) in gcs_final_report.txt are
  maintained inside each satellite *session* on the GCS. After a reconnect, a new
  receiver rebuilds histograms; end-of-run values can look “saturated” (very large
  placeholder-style numbers) if the last session had too few samples. Prefer
  steady-state "PERFORMANCE REPORT" lines or the per-packet telemetry_rx latency_us
  stream for definitive latency proof.

- fault_received_count / interruptions now *accumulate* across reconnects in code
  (ground\src\fault_mgr.rs) so gcs_final_report reflects all sessions.

- If the second satellite session hits "RECOVERY EXCEEDED 200ms — MISSION ABORT",
  later faults on that process may not be sent to the GCS; that is visible in
  satellite.log and does not invalidate GCS behavior for the first session.
